# 08 — M2 Execution Extension Contract

## Status and governing sentences

This document freezes the smallest provider-neutral semantic contract for M2.
It is a documentation-only gate. It does not implement an adapter, fake,
provider integration, Supervisor, recovery policy, or M3 decision.

> **Execution Extension produces execution facts; Managed Runtime decides durable semantics.**

> **Observation is evidence, not a verdict.**

M2 consumes an execution admission already created by M1 and reports what the
live execution boundary can observe. Managed Runtime remains the only owner of
durable Run, Attempt, Binding Epoch, state, outcome, and recovery meaning.

## 1. M2 purpose

M2 is the live execution extension between an admitted M1 Attempt and a
provider, agent, process, session, transport, tool, event stream, or workspace.
It supplies a replaceable execution boundary without making provider behavior
the source of durable semantics.

The minimum M2 result is a correlated set of execution facts. A successful
adapter call is not itself a successful execution, Attempt, or Run.

## 2. Scope

M2 defines the semantics of:

- immutable `ExecutionIntent` input from Managed Runtime;
- live `ExecutionHandle` references;
- `ExecutionObservation` facts and their correlation;
- `start`, `observe`, `inspect`, and `terminate` operations;
- process, session, transport, tool, event, workspace, timeout, disconnect,
  cancellation, and execution-handle facts;
- a provider-neutral fake Extension acceptance model.

This is a logical internal contract, not an API, SDK, wire format, schema, or
provider capability catalog.

## 3. Ownership

### M2 / Execution Extension owns

- creation and lifecycle of live process, session, transport, tool, event, and
  workspace primitives;
- execution-handle allocation and live-handle bookkeeping;
- provider-facing execution, cancellation, cleanup, reconnect, and inspection;
- collecting and emitting facts that the live boundary can observe;
- preserving correlation supplied in an admitted intent whenever the provider
  permits it;
- returning provider/tool-specific receipts, probes, or capability references
  as opaque facts when available.

### Managed Runtime / M1 owns

- `Run`, `Attempt`, `Binding`, and immutable `Binding Epoch` identity;
- durable state, transitions, history, version, and fencing;
- durable `UNKNOWN`, `RESOLVING`, evidence, and recovery facts;
- durable outcome, artifact provenance/trust, and isolation-policy acceptance;
- interpretation of observations and every retry, new-Attempt, compensation,
  termination, or terminal-outcome decision.

## 4. Non-ownership

The Extension is not a durable Attempt store, Run owner, Binding Epoch
authority, artifact-trust authority, recovery authority, or Supervisor. It
cannot create Attempt identity, mutate M1 state, change an epoch, declare a
Run or Attempt terminal, or choose what to do after an uncertain observation.

An Extension may accept or reject a live request according to its capabilities,
but that acceptance is only an execution fact. Runtime decides whether the
request was admitted and what the fact means durably.

## 5. ExecutionIntent

`ExecutionIntent` is the minimum immutable, provider-neutral input sent from
Managed Runtime for one admitted live execution boundary. It contains:

| Field | Semantic requirement |
|---|---|
| `run_id` | Existing M1 Run identity; never generated by the Extension. |
| `attempt_id` | Existing M1 Attempt identity; exactly the Attempt being executed. |
| `epoch_id` | Existing immutable Binding Epoch identity. |
| `binding_epoch` | Read-only epoch reference or snapshot sufficient to apply the admitted binding constraints. |
| `request` | Provider-neutral execution request or opaque Runtime-owned request reference. It describes what Runtime admitted, not a provider API shape. |
| `execution_policy` | Runtime-owned execution constraints such as permitted lifecycle, timeout, cancellation, and observation expectations. |
| `isolation_requirements` | Runtime-owned process, workspace, network, credential, tenant, or equivalent isolation constraints. |

The intent is immutable for the lifetime of the execution boundary. An
Extension must not rewrite its identities, policy, isolation requirements, or
epoch. Provider-specific options may be represented inside the binding epoch
or provider implementation, but they are not additional M2 semantic fields.

The triple `(run_id, attempt_id, epoch_id)` is the required semantic binding.
The Extension must reject an intent whose identities cannot be carried
forward, rather than substituting a new identity.

## 6. ExecutionHandle

An `ExecutionHandle` is an opaque live reference allocated or returned by the
Extension for a concrete execution boundary.

- **Identity:** It identifies the Extension's currently addressable live
  process/session/transport/tool boundary. It is not a Run, Attempt, Epoch, or
  durable outcome identity.
- **Scope:** A handle is scoped to one `(run_id, attempt_id, epoch_id)` and to
  the Extension authority that issued it. It must not be reused for a
  different Attempt or Epoch.
- **Durability:** It is a live reference, not a durable semantic record. M1
  may persist the last-known opaque value as a seam for correlation, but that
  value is not proof that the live execution still exists and is not required
  to survive Extension restart.
- **Staleness:** A handle is stale when the Extension can no longer guarantee
  that operations address the same live boundary. The Extension reports that
  fact; it does not infer termination, side-effect absence, failure, or retry.
- **Reuse and reconnect:** Reconnect may return the same handle or a new one
  only as an execution fact. Reconnect does not automatically imply Attempt
  continuity. Runtime must not reuse a handle across Attempt identity.
- **Absence:** A missing handle, null handle, or handle that cannot be
  recovered is an observation gap, not proof of termination.

## 7. ExecutionObservation

An `ExecutionObservation` is an immutable fact emitted by the Extension from a
specific operation or asynchronous event source. At semantic level it carries:

| Field | Requirement |
|---|---|
| correlation | `run_id`, `attempt_id`, and `epoch_id` whenever the provider permits; never guessed. |
| `execution_handle` | The relevant handle when available; otherwise explicit absence. |
| category | One of the provider-neutral categories below. |
| fact | Provider-neutral fact payload or an opaque provider reference. |
| observed_at | Extension observation time; operation time may be included when known. |
| observation_id / sequence | An Extension-issued identity or ordering marker when available, for deduplication and gap reporting. |

The categories are semantic, not an exhaustive provider enum:

- `started` — a live boundary was accepted or created;
- `running` — execution was observed active;
- `waiting` — execution was observed waiting for input, a tool, or a provider event;
- `output_event` — output or stream/event data was observed;
- `tool_result` — a tool result, receipt, probe, or undo-capability reference was observed;
- `disconnected` — a process, session, or transport link became unreachable;
- `terminated` — termination or exit was observed, including its scope;
- `inspect_result` — a point-in-time inspection fact;
- `error` — an execution or adapter error fact, including timeout/cancellation details.

Categories describe what was observed. They do not map one-to-one to M1
states, terminal outcomes, side-effect conclusions, or recovery actions.

## 8. Semantic contract for adapter operations

All operations are requests against one admitted `ExecutionIntent` and, after
`start`, its `ExecutionHandle`. The syntax, transport, and return type are
implementation choices; the following facts and authority rules are not.

### `start`

1. Runtime receives an acknowledgement fact: accepted, rejected, or
   inconclusive, plus a handle and `started`/`error` observation when the
   Extension can provide one.
2. Extension owns creating and initializing live primitives and reporting
   their directly observable status.
3. Extension does not decide Attempt admission, Attempt continuity, epoch
   changes, success/failure, retry, or new Attempt identity.
4. `start` cannot cause a durable state transition directly. Runtime may later
   persist the fact and perform an M1 transition under version/fence rules.
5. A start timeout, disconnect, or partial response is an inconclusive fact.
   It does not prove that no process or side effect exists, and it does not
   become `FAILED` by translation.
6. The acknowledgement and every resulting observation preserve the intent's
   Run/Attempt/Epoch correlation; the handle is included when available.

`start` is not equivalent to successful execution.

### `observe`

1. Runtime receives zero or more attributed observations, a live snapshot, an
   event cursor, or an explicit gap/inconclusive fact.
2. Extension owns reading live process/session/transport/tool/event/workspace
   facts and making a best effort to preserve ordering and deduplication.
3. Extension does not infer a terminal result from silence, missing events, or
   an absent handle, and does not decide recovery or retry.
4. `observe` cannot cause a durable state transition directly.
5. Observe timeout or disconnect returns an observation gap, timeout, or
   disconnected fact. No response is not evidence of termination or no side
   effect.
6. Each observation carries the original Run/Attempt/Epoch and handle when
   available; uncorrelatable data is marked uncorrelatable rather than attached
   to a guessed Attempt.

### `inspect`

1. Runtime receives a point-in-time fact about the referenced handle and any
   visible process/session/transport/tool/workspace state, such as live,
   terminated-observed, not-found, stale, or unknown-to-inspect.
2. Extension owns the probe and its freshness limits.
3. Extension does not interpret the probe as proof of side-effect absence,
   safe retry, Attempt completion, or Run outcome.
4. `inspect` cannot cause a durable state transition directly.
5. Inspection timeout or disconnect yields an inconclusive inspection fact.
   A stale or not-found handle remains compatible with an unknown live or
   previously completed side effect.
6. The result is correlated to the requested Run/Attempt/Epoch and handle when
   the provider permits; the freshness time and inability to correlate are
   explicit facts.

`inspect` returns facts, not recovery decisions.

### `terminate`

1. Runtime receives facts such as termination requested/accepted, cancellation
   observed, process/session exit observed, cleanup incomplete, or
   termination-not-observed.
2. Extension owns the best-effort live stop, cancellation, and cleanup
   mechanisms available to it.
3. Extension does not decide whether the Attempt or Run is `CANCELLED`,
   `FAILED`, `UNKNOWN`, or otherwise terminal, and does not decide whether a
   side effect was committed or undone.
4. `terminate` cannot cause a durable state transition directly.
5. Timeout or disconnect means termination was not fully observed. It is not
   proof that execution stopped or that side effects were prevented.
6. Every termination fact preserves Run/Attempt/Epoch correlation and the
   handle/reason when available.

`terminate` reports execution facts; Runtime owns final semantic outcome.

## 9. Correlation rules

1. Runtime sends the immutable `(run_id, attempt_id, epoch_id)` triple with
   every operation. The Extension echoes it on every synchronous and
   asynchronous observation whenever the provider permits.
2. An observation with a handle must identify the same triple for which that
   handle was issued. A mismatched triple is a correlation error, not a new
   Attempt or epoch.
3. If a provider cannot supply one correlation component, the Extension
   reports the missing component and its correlation limitation. It must not
   guess, copy the latest active Attempt, or silently drop the fact.
4. Observation IDs, cursors, and sequence markers are for attribution,
   ordering, deduplication, and gap detection. They do not grant transition
   authority and are not durable Attempt identity.
5. Late, duplicated, reordered, or stale observations remain evidence with
   their original observed time and correlation. Runtime decides whether they
   are relevant to a durable transition.
6. Correlation to an execution handle is optional only when no handle exists;
   Run/Attempt/Epoch attribution remains required whenever the provider can
   preserve it.

## 10. Disconnect, timeout, and stale-handle semantics

The Extension reports the boundary it can observe; it does not fill an
observation gap with a semantic conclusion.

| Condition | M2 fact | M2 must not conclude |
|---|---|---|
| transport/session disconnect | `disconnected` with scope, time, last-known handle, and any last-known sequence | process terminated, side effect absent, Attempt failed, or retry safe |
| operation timeout | `error`/timeout or inconclusive result with operation correlation | execution failed or did not start |
| missing handle | explicit absent-handle/gap fact | execution terminated |
| stale/not-found handle | inspection/operation fact that the reference is no longer addressable | no side effect, terminal Attempt, or new Attempt permission |
| reconnect | same/new handle and observed continuity facts, if any | automatic Attempt continuity or epoch continuity |
| event gap or out-of-order stream | gap/ordering fact with cursor/sequence information | missing event had a particular value |

Runtime may persist these facts, move an Attempt to M1 `UNKNOWN` when its own
transition rules require evidence, or ask M3 to interpret them. None of those
durable decisions is performed by M2.

## 11. State-transition authority boundary

The only durable semantic transition authority is Managed Runtime through the
M1 state machine, expected-version checks, and fencing rules. The Extension
may request an operation and return facts; it may not write a durable
transition as a side effect of `start`, `observe`, `inspect`, or `terminate`.

The following invariants are mandatory:

- Extension cannot create durable Attempt identity.
- Extension cannot change Binding Epoch.
- Extension cannot mark Run `SUCCESS`.
- Extension cannot interpret `UNKNOWN` as `FAILURE`.
- Extension cannot decide retry or new Attempt.
- Execution observation is evidence, not verdict.
- A missing execution handle is not proof of termination.
- Disconnect is not proof of no side effect.
- Reconnect does not automatically imply Attempt continuity.
- `start` is not equivalent to successful execution.
- `inspect` returns facts, not recovery decisions.
- `terminate` reports execution facts; Runtime owns final semantic outcome.
- All observations must be attributable to the correct Run/Attempt/Epoch
  whenever the provider permits correlation.

## 12. Fake Extension acceptance model

The fake is a future provider-neutral contract test double, not part of this
task. It must be designable without adding semantic decisions and must support
deterministic scenarios that return only the facts defined above:

1. normal start → running/output/tool-result → observed termination;
2. accepted start with delayed or absent first observation;
3. start timeout or partial response with an unknown live boundary;
4. disconnect during execution, including an optional side-effect/receipt
   fact that remains non-verdict evidence;
5. inspect of live, terminated-observed, stale, not-found, and unknown handles;
6. duplicate, reordered, and gapped observations with stable IDs/cursors;
7. reconnect returning the same or a new handle without asserting Attempt
   continuity;
8. terminate accepted, terminate observed, cleanup incomplete, and terminate
   not observed.

Acceptance checks must prove that the fake cannot create an Attempt, mutate an
epoch, write M1 state, mark success, translate disconnect/timeout to failure,
or decide retry/new Attempt. They must also prove every emitted fact preserves
the supplied correlation when the scenario permits it.

## 13. Explicit M2 non-goals

M2 does not implement or decide:

- a real Codex, Claude, Pi, or other provider adapter;
- a provider SDK or API/wire schema;
- Supervisor or reconciliation loops;
- verification policy, receipt interpretation, idempotency policy, retry
  admission, new-Attempt lineage, compensation, or termination policy;
- artifact identity, provenance, integrity, or trust decisions;
- durable Run/Attempt/epoch state, migrations, or M1 semantic changes;
- a claim that process/session restart restored the original execution;
- a universal mapping from an execution fact to `SUCCEEDED`, `FAILED`, or
  `CANCELLED`.

## 14. M2 acceptance gate

M2 is **READY FOR IMPLEMENTATION** only when this document is the semantic
source of truth and all of the following are closed:

- `ExecutionIntent` semantics are frozen;
- `ExecutionHandle` identity, scope, durability, staleness, and reuse rules
  are frozen;
- observation correlation is frozen;
- `start`, `observe`, `inspect`, and `terminate` semantics are frozen;
- disconnect, timeout, event-gap, and stale-handle semantics are frozen;
- Extension non-ownership and M1 transition authority are explicit;
- no M3 recovery-decision semantics leak into M2;
- a provider-neutral fake Extension can be designed from this document without
  additional semantic decisions.

This gate authorizes a later implementation task only. It does not authorize
real-provider integration in this documentation change.

## 15. Mapping to future M3 recovery inputs

M3 consumes M1 durable facts together with the following M2 evidence; M2 does
not perform the interpretation:

| M2 evidence | Possible M3 input |
|---|---|
| `started`, `running`, `waiting` | Whether the execution boundary was observed at a particular time and phase. |
| `output_event`, `tool_result` | Output, result, receipt, probe, operation-reference, and event-sequence evidence. |
| `disconnected`, timeout, event gap | A bounded uncertainty boundary for verification and recovery analysis. |
| `inspect_result` | Freshness-qualified live/stale/not-found/terminated observations. |
| `terminated`, cancellation, cleanup facts | What the Extension observed about stop/exit, without a semantic outcome. |
| `error` | Provider/transport/process/tool error facts and their scope. |
| handle identity and handle transitions | Evidence about which live reference was addressable, never Attempt lineage by itself. |

M3 may request verification, retry admission, a new Attempt, compensation,
termination, or a terminal transition only after applying its own policy to
these facts and the durable M1 record.

## 16. Valid and invalid behavior examples

### Valid

- `start` returns `accepted` plus handle `h1` and a `started` observation for
  the supplied Run/Attempt/Epoch; Runtime later decides whether to persist or
  transition based on M1 rules.
- `observe` reports a transport disconnect with `h1`, the last sequence, and
  the correct correlation. Runtime records an observation gap or `UNKNOWN`
  evidence rather than assuming failure.
- `inspect(h1)` reports `stale` at time `t2`; Runtime can ask M3 to interpret
  the fact, but no Attempt is created automatically.
- `terminate(h1)` reports `accepted` and later `termination-not-observed`;
  Runtime retains uncertainty about the live boundary and side effects.
- A reconnect returns `h2` and states only that the provider cannot prove
  continuity; Runtime keeps identity decisions outside M2.

### Invalid

- The Extension inserts a new Attempt row, changes `epoch_id`, or reuses `h1`
  for another Attempt.
- The Extension turns `start` accepted into Run `SUCCEEDED`, or turns a
  timeout/disconnect into Attempt `FAILED`.
- The Extension reports a missing handle as proof that the process stopped or
  that no side effect occurred.
- The Extension claims reconnect restored Attempt continuity without a Runtime
  decision, or makes `inspect` return “retry now”.
- The Extension treats a tool receipt as universal proof of success or makes
  `terminate` claim that an external side effect was undone.
